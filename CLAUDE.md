# MINDOT Project Guidelines

## Architecture

- Code is organized by feature under `src/features/<feature>` (e.g. `board`, `notes`), not by technical layer. `src/app` stays thin: routing and composition only.
- Shared, generic UI lives in `src/components/ui`; site chrome (header, footer, page shell) lives in `src/components/layout`; brand assets live in `src/components/brand`.
- Design tokens (color, radius, shadow, motion, z-index) are defined once in `src/styles/tokens.css` and mapped into Tailwind's `@theme` in `src/app/globals.css`. Components should reference tokens/utilities, not hardcoded hex values or one-off spacing.

## Note / template system

- A "note" (content, author, position, template reference) is data; a "template" (paper tone, shape, attachment, font) is a visual style registered in `src/features/notes/config/templates.ts`. New visual styles — including future seasonal/event collections — are added by registering a new template, never by hardcoding a one-off note component.
- Special-occasion scheduling lives on the template itself (`category`, `occasion`, `availableFrom`/`availableUntil`, `enabled`) and is enforced by `isTemplateAvailable`/`getActiveNoteTemplates`. Any UI that lets someone pick a template (the write flow) must go through `getActiveNoteTemplates`, not the raw `noteTemplates` array — the board preview's curated sample notes are the one deliberate exception, since they reference fixed templates directly.
- `Note` takes a `variant`: `"board"` (absolutely positioned via `sm:` breakpoint, part of the scattered board preview — the default, with a mobile horizontal-scroll fallback), `"static"` (normal document flow, still rotated — a single note shown on its own, e.g. the write-flow preview), or `"world"` (always absolutely positioned, no mobile fallback — one note inside one tile of the interactive infinite board, at percentage coordinates relative to that tile's container). All three share the same template/paper/shape/attachment rendering — reuse `Note` with the right variant rather than building a second note renderer.
- **New Standard cards** (`standard-*`, first: `standard-classic`) are image-backed templates (`image` + `contentArea`), so Picker, Preview, DUVAR, share card and PDF all draw the same artwork. Each sets `contentTextSize: "spacious"`: DOM text is sized in `cqw` of the card (`SPACIOUS_IMAGE_BACKED_TEXT_SCALE`, `lib/textScale.ts`) and mirrored in px by `SPACIOUS_IMAGE_BACKED_FONT_PX` (`noteCardSatori.tsx`) — change both together. Ship a web derivative under `public/images/standard/web/` (cropped to the paper, ~600px), never the designer's full-size master: the share card and PDF inline the artwork as base64. One fixed color per design (`paper`); there is no user color choice and no CSS recoloring. `contentArea` is measured on the asset, not guessed — see the `standard-classic` entry's comment. Every runtime asset must pass `npm run assets:validate-standard` (`src/lib/assets/`: a dependency-free PNG decoder measures real alpha — transparent surroundings, no opaque backdrop, ≤ 500 KB, ≤ 1024px, no text/EXIF metadata); the gate never fixes an image itself. Cards so far: `standard-classic` (150 characters), `standard-minimal` (`web/minimal.png`) and `standard-quote` (`web/quote.png` — its `contentArea` is measured inside the printed frame and clear of the quote marks, not from the paper edge). Satori never breaks a word by itself, so all three of `MemoryNoteCard`'s text branches (`noteCardSatori.tsx`) — image-backed cards, standard CSS cards and the football disc — use `wordBreak: "break-word"`, the DOM's `break-words` equivalent: only a single word too wide for the line is broken inside the card, normal words wrap as before. The share card and the PDF render the same component, so this is the one place for it — never `break-all`.
- **Per-card message limit.** `MESSAGE_MAX_LENGTH` stays the global 150. A template may set a lower `maxCharacters` — the new illustrated Standard cards after Classic use 100 in V1 (`standard-minimal`, `standard-quote`); every card without it keeps 150. Always read it through `maxMessageLength(templateId)` (`features/messages/lib/messageLength.ts`): the write form's counter/`maxLength`, the archive edit dialog, `submitMessage` (after template validation) and `submitMessageRevision` (from the *stored* message's template, after the ownership check) all use it — the server checks are the boundary, never only the textarea.
- `NoteData.authorImage` (optional) renders a small circular avatar at the note's corner — only ever populated from the board's public author contract (never set for anonymous notes); see "Public author privacy contract" below.

## Internationalization

- Interface language and thought-content language are separate concepts. Interface strings live in `src/i18n/translations/{locale}.ts`, one file per locale, all conforming to the `Dictionary` type in `src/i18n/translations/types.ts` — TypeScript will refuse to compile a locale file that's missing or has an extra key, so translations can't silently drift. `src/i18n/config.ts` is the single source of truth for supported locales (currently en, tr, de, fr, es); add a language by adding it there and creating its dictionary.
- Locale state is client-side only (`src/i18n/LocaleProvider.tsx`, a React context + `useLocale()` hook), initialized from `localStorage` → browser language → English, and persisted back to `localStorage` on change. This means any component that renders translated UI text must be a Client Component. There is no URL-segment-based routing (`/en/...`, `/tr/...`) — that's a reasonable future upgrade for SEO, not implemented here.
- To keep Server Components server-rendered where the content doesn't need translation (the board preview's sample notes, for instance), a page can stay a thin Server Component that fetches server-only data (session, invitation) and hands it as props to a Client Component that does the actual rendering via `useLocale()`. See `src/app/invite/[token]/page.tsx` + `InvitePageContent` for the pattern.
- A thought's own language is optional metadata (`NoteData.language`, `Message.language`) and is never auto-translated — the original text is always the canonical content.

## Authentication

- Google sign-in (plus Sign in with Apple when configured — see below; Credentials for the one admin), via next-auth v5 (`next-auth@5.0.0-beta.32`, `src/features/auth/auth.ts`), **JWT session strategy — no Auth.js database adapter.** The session itself still lives in an encrypted cookie; the `jwt` callback separately upserts a row into our own `users` table (via `userRepository`) on every fresh sign-in, so messages/invitations have a real foreign key to point at. A user's `role` is resolved once at sign-in (from the DB) and embedded in the JWT, so `session.user.role` needs no extra DB call. The one per-request read is an existence check (`userRepository.isActiveAccount`, a primary-key lookup) so a deleted account's JWT stops authenticating immediately — see "Account deletion" below. Requires `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `AUTH_SECRET` at runtime (see `.env.example`); without them, sign-in fails at request time with a clear error rather than faking a session.
- Read session state with `await auth()` directly in Server Components/Server Functions — there is no middleware/proxy.ts in this project, deliberately, since Next.js 16 renamed middleware to `proxy.ts` and Auth.js's documented middleware pattern predates that rename. Gating a page is: check `auth()` in the page's Server Component, pass the result down as a plain prop.
- Sign-in/sign-out go through Server Functions (`src/features/auth/actions.ts`) bound into a `<form action>` (see `GoogleSignInButton`), not `next-auth/react`'s client hooks.

- **Sign in with Apple (web)** — `next-auth/providers/apple`, registered only when `AUTH_APPLE_ID` (Services ID), `AUTH_APPLE_SECRET` and `AUTH_APPLE_TOKEN_KEY` are all set, so no page ever shows a button that can't work. Every normal-user sign-in spot (`/login`, `/me*`, `/notifications`, `/memory/[id]`, `WriteThoughtForm` for `/write` + invites) renders the one `SignInOptions` component (Google, plus Apple when the root layout's `SignInOptionsProvider` says it's configured) — add a provider there, never per page. `AUTH_APPLE_SECRET` is a client-secret JWT (≤ 6 months) generated offline by `npm run auth:apple-secret` (`src/lib/createAppleClientSecret.ts`, Node crypto only) from `APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY_PATH` — the `.p8` key is never a runtime variable and must live outside the repo (the script refuses one inside it). Apple accepts HTTPS origins only; the return URL is `<AUTH_URL>/api/auth/callback/apple`.
  - **Identity**: an Apple user's `users.id` is `apple:<sub>` (`appleUserId`, `features/users/lib/providerIds.ts`); Google rows keep the bare Google `sub` — no migration. `upsertFromAppleProfile` always creates role `"user"` and never rewrites role/email later; the Apple `jwt` branch additionally forces the session role to `"user"`, so Apple can never produce an admin session. Both OAuth branches of the `jwt` callback key on `account.provider` — never on "profile has sub + email", which Apple's profile also satisfies.
  - **No email-based account merge.** `signIn` runs `userRepository.classifyProviderSignIn` first: a *new* Google or Apple identity whose email already belongs to a different account (the admin's included) is refused → `/login?error=account-exists`. There is no verified account-linking flow, and linking by matching email would be a takeover path. A new Apple identity with no email → `/login?error=apple-email-missing`.
  - **Name**: taken only from Apple's first-consent `user` form field (unsigned — trimmed, control characters stripped, 80-char cap; `parseAppleProfile`), never from the email. Auth.js's default Apple profile falls back to the email, which with "Hide My Email" would publish a private-relay address on named notes. The private-relay email is stored like any email (account deletion's confirmation step shows it to the user).
  - **Cookies**: Apple returns via a cross-site form POST, so the `state`/`nonce`/`callbackUrl` cookies are `SameSite=None; Secure` when Apple is enabled on an HTTPS origin (the session cookie stays `Lax`; Google is unaffected). `pages: { signIn: "/login", error: "/login" }` — a cancelled consent or failed check returns to `/login`, which renders only an allow-listed or generic message, never the raw `?error=` value.
  - **Token revocation on account deletion (App Review 5.1.1(v))**: the `jwt` callback's Apple branch stores `account.refresh_token` — available only in that sign-in's token response — in `apple_sign_in_tokens`, encrypted with AES-256-GCM under `AUTH_APPLE_TOKEN_KEY` and bound to `user_id` as associated data (`features/auth/lib/appleTokenCrypto.ts`, `appleTokenRepository`). Never plaintext, never in the JWT, never logged; Google/admin accounts store nothing. `deleteUserAccount` (`features/users/accountDeletion.ts`) — what `deleteOwnAccount` calls — **revokes at Apple first** (`/auth/revoke`, authenticated with the same `AUTH_APPLE_SECRET` client-secret JWT), then runs the unchanged atomic `deleteAccount`, which also removes the token row. A `failed` revoke (Apple unreachable/5xx, or our secret rejected — e.g. expired) deletes nothing and asks the user to retry; `invalid_grant` (already revoked/expired) or no stored token proceeds; Apple switched off or a token that no longer decrypts proceeds with a logged warning. The two systems can't share a transaction, and this ordering never leaves a half-deleted account or an owed revocation — so no retry queue.

## Authorization / admin role

- Roles live on the `users.role` column (`"user" | "admin"`), not in an env var checked ad hoc in UI code. **EPIC 035: Google sign-in never grants admin, regardless of email — full stop.** `upsertFromGoogleProfile` (`src/features/users/repository.ts`) always creates a new Google row with `role: "user"`, unconditionally; there is no path anywhere in the Google callback where a Google account's email is compared against anything to decide role. The earlier `ADMIN_EMAILS` bootstrap mechanism was removed entirely (not just disabled) because it violated the same rule it's now documented against. Admin is exclusively the one dedicated Credentials identity provisioned out-of-band by `npm run db:create-admin` (`ADMIN_EMAIL`/`ADMIN_PASSWORD`, optionally `ADMIN_USERNAME` for the row's `username` column — see `.env.example`) — see "Authentication" below for the full Credentials-vs-Google split. **EPIC 036: `/admin/login` itself now asks for email + password, not username + password** (`getCredentialsByEmail` in `src/features/users/repository.ts`) — this is a completely separate lookup from Google's OAuth email and does not weaken the invariant above: a Credentials sign-in still requires the correct password hash for the one admin row, and a Google sign-in still can never produce `role: "admin"` no matter what email it carries. Add more admins only by updating the `role` column directly (or a future admin-management UI), never by email matching at Google sign-in time.
- Never hardcode an email check in a component. Authorization is always `session.user.role === "admin"`, checked server-side. Every admin-only Server Function independently re-verifies this itself — a page-level gate (e.g. `/admin/moderation`'s Server Component only fetching data when authorized) is defense in depth, not the actual security boundary.

## Account deletion

- Self-service, irreversible, from `/me` (`DeleteAccountSection`, `features/users/components/`): an explanation step, then retyping the account's email. `deleteOwnAccount` (`features/users/account-actions.ts`) takes no user id — the account is always the session's — re-checks the typed email server-side, refuses the admin account (provisioned out-of-band, never self-service), and signs the browser out on success.
- `userRepository.deleteAccount` is one transaction, and the deliberate cross-table exception to "a feature only touches its own tables" (same precedent as `tokenRepository.consumeForMemoryPdfUnlock`). The user's own row is **physically deleted**: its id is their Google `sub` — a personal identifier — and keeping it would let the same Google account revive the old row on its next sign-in (`upsertFromGoogleProfile` upserts on id). Records that must outlive the account are re-pointed to a fresh, random-id **tombstone** row (`users.deletedAt` set, no email/name/image/publicId, can never sign in):
  - **Deleted:** the user row, their notifications, their user blocks (both directions), their likes (like counts decremented), never-published (pending/rejected) messages nothing else references, memory projects with no order/unlock/access code.
  - **Anonymized onto the tombstone:** published/archived messages (author name `"anonymous"`, `isAnonymous`, off the personal wall, pending edits dropped — they stay on the board because approved placement is permanent and other users' keepsakes/orders reference them), memory projects with an order/unlock/code, `physical_orders`, `token_ledger`, `token_wallets` (remaining balance stays with the tombstone, unspendable; `balance == SUM(ledger)` still holds per id), `memory_pdf_unlocks`, `digital_access_codes.redeemedBy`, filed reports.
- Every FK to `users.id` is handled in that method. **Adding a new FK to `users.id` means updating `deleteAccount`** — otherwise its final `DELETE` fails and the whole deletion rolls back (safe, but broken for users).
- Stale sessions: JWTs can't be revoked, so the `jwt` callback re-checks `isActiveAccount` on every request and returns `null` (signed out, cookie cleared) for a deleted account. A database *error* during that check keeps the session (fail-open) rather than signing everyone out during an outage.
- Tombstones are excluded from `userRepository.listAll()` (`/admin/users`). **Open legal TODO:** statutory retention for the retained purchase/ledger/order records, and the privacy policy's deletion wording, need professional review against this behavior before launch.

## User blocking

- `user_blocks` (`blockerUserId`, `blockedUserId`, `createdAt`; composite PK = idempotent re-block; `CHECK` against self-blocks) — **directional**: A blocking B hides B's content from A only; mutual blocking is simply two rows. `features/blocks/` owns it (`blockRepository`, `actions.ts`, components). Visibility is applied at **read time only** — blocking never changes a message's status, placement, moderation, or reports.
- **Anonymous notes are never filtered, and their authors can never be blocked.** Hiding a blocked user's anonymous notes would let the blocker infer who wrote them, breaking the anonymity contract; `blockUser({ messageId })` resolves only an approved, *named* note's author and returns the same `not-found` for anything else. Filtering is `is_anonymous = true OR author_id NOT IN (<viewer's blocked ids>)`, in SQL (`excludeNamedAuthors` in `messages/repository.ts`) — the blocked-id list is one small query per request, passed in as an exclusion list rather than a cross-feature join.
- **Authorization**: `blockUser`/`unblockUser` take the *target* as `{ publicId }` or `{ messageId }` — never a raw database id (a Google `sub`) — and the *blocker* is always the session's account. Nothing ever returns who has blocked a given user. The admin surfaces (`/admin/*`) are never block-filtered.
- **Cache isolation — public and personal are separate URLs.** `/api/board` and `/api/board/search` by default never read the session and stay `public` and cacheable exactly as before; `?personal=1` reads the session, filters, and responds `private, no-store`. Because the variants differ by URL, no browser/CDN cache can serve one viewer's filtered result to anyone else (or an unfiltered public copy to a blocker). A signed-in viewer's board (`useTileCache({ personal, generation })`, `BoardDiscoveryPanel({ personal })`) uses the personal variants; bumping `generation` after a block refetches every tile at once.
- **Per-request pages filter server-side**: `/board`'s initial tile, `/u/[publicId]` (`getPublicWall(..., viewerId)` → a `"blocked"` state that, like `"disabled"`, returns before any message query — `generateMetadata` included, so the blocked person's text isn't in the page head either), and direct note URLs `/share/[id]` + `/memory/[id]` (`isMessageAuthorBlockedBy` → `BlockedNoteNotice`). Public artifacts with no viewer (OG images, share-card PNGs) stay the public view.
- **The ISR homepage is the one exception**: rendered once for everyone, so its hero notes are hidden client-side via `useHiddenMessageIds` → `/api/blocks/hidden-messages` (private, `no-store`, capped at 20 ids, never flags anonymous notes). A blocked note can therefore flash briefly on the homepage before the lookup returns — known and accepted; don't "fix" it by making the homepage dynamic without deciding that deliberately.
- Blocks are managed on `/me` (`BlockedUsersSection`) and on the blocked user's wall; `blockUser` calls `ensurePublicId` on the target so every block stays listable and undoable by public id.

## Database & repository pattern

- PostgreSQL via Drizzle ORM (`drizzle-orm` + `postgres` driver), schema in `src/lib/db/schema.ts`, connection in `src/lib/db/client.ts`. `getDb()` is lazy — it only throws if `DATABASE_URL` is missing when a query actually runs, never at module-import time, so `next build` never requires a live database (every route that touches it is a dynamic route, never prerendered).
- Every feature (`users`, `invitations`, `messages`) exposes a repository **interface** with a Drizzle-backed implementation behind it (e.g. `InvitationRepository`, `MessageRepository`). Nothing outside a feature's `repository.ts` talks to its Drizzle table directly — Server Components, Server Functions, and API routes all go through the interface. Preserve this shape if the storage backend ever changes again.
- After editing `schema.ts`: `npm run db:generate` then `npm run db:migrate`. See README.md for local Postgres setup and `npm run db:seed`.
- **`drizzle.config.ts` loads `.env.local` itself** (same `process.loadEnvFile` try/catch as `seed.ts`/`verify.ts`) — required because `drizzle-kit` is a standalone CLI, not Next.js, so it never auto-loads `.env.local` the way `next dev`/`next build` do. Without this, every bare `db:generate`/`db:migrate`/`db:push`/`db:studio` invocation would fail with an empty `DATABASE_URL` despite `.env.local` being correctly filled in — confirmed as a real, reproducible bug in EPIC 015 (`npm run db:migrate`, run exactly as README's own "Getting started" steps document, failed until this fix). A CI environment that sets `DATABASE_URL` directly with no `.env.local` file present is unaffected.

## Writing experience

- `WriteThoughtForm` (`src/features/messages/components/WriteThoughtForm.tsx`) is the one writing UI, used both standalone (`/write`) and inside an invitation (`/invite/[token]`). Its template picker (`TemplatePicker`, `src/features/notes/components/TemplatePicker.tsx`) and its live preview both render the real `Note` component — never a mock/approximation of a template. Reuse `TemplatePicker` for any future place someone picks a note style rather than rebuilding a picker.
- The anonymous/named choice is two explicit, labeled options (not a checkbox) and defaults to anonymous — see "Anonymous vs named sharing" below for why the server, not this form, is what actually enforces it.

## Anonymous vs named sharing

- `isAnonymous` is decided by the user in `WriteThoughtForm`, but **enforced in `submitMessage`** (`src/features/messages/actions.ts`): when anonymous, the real display name the client sent is discarded before the message is ever created — the stored `authorName` is the literal string `"anonymous"`, not a real name with a client-side flag asking the UI to hide it. The browser is never trusted with this. See "Public author privacy contract" for the board-read side of the same guarantee (an anonymous message's author is never even looked up).
- The live preview shows the Google avatar (`sessionUser.image`) only when the "share my identity" option is selected — this is a UI convenience for what the user is *about* to publish, not the privacy boundary itself; that boundary is server-side per above.

## AI moderation abstraction

- `src/features/moderation/` defines `ModerationService` (`analyzeMessage(content, context) -> ModerationResult`, one `decision` of `"safe" | "review" | "blocked"` plus categories/reason/provider/confidence) and `getModerationService()` (`service.ts`), which selects an implementation by the `AI_MODERATION_PROVIDER` env var. `submitMessage` calls it once per submission and stores the result on the message — it never changes what `submitMessage` does with the message itself.
- The only implementation that exists is `providers/devFallback.ts` — no external AI credentials exist anywhere in this project. It is explicit about what it is: its `provider` name is literally `"dev-fallback"`, and its `reason` text says outright that no real analysis happened. It never returns `"safe"` (a heuristic has no basis to clear content on the merits) and only reaches `"blocked"` for mechanically obvious spam patterns (repeated characters) — everything else is `"review"`. Do not make this provider more clever; if it starts doing anything that looks like real content understanding, it stops being honest about being a fallback. A real provider is a new file under `providers/` plus one new `case` in `service.ts` — see the comment there.
- **AI moderation data is admin-only.** `aiModerationStatus`/`Provider`/`Categories`/`Reason`/`Confidence`/`ModeratedAt` live on the `messages` row and are read by the moderation queue; they are not part of `BoardTileMessage` (the public contract) and must never be added to it.

## Human moderation authority

- AI moderation is pre-screening, never a publishing decision. Every message reaches `submitMessage`'s end the same way — `status: "pending"` — regardless of the AI decision, including `"blocked"`. The only thing that moves a message out of `"pending"` is an admin calling `approveMessage`/`rejectMessage` (`src/features/messages/moderation-actions.ts`), which independently re-checks `session.user.role === "admin"` itself. Do not add a code path that skips this for any AI decision, including `"safe"`.
- Rejected messages are kept (for audit/history), never deleted, and are never returned by any public-facing query.
- Approving a message assigns its board placement (`tileX`/`tileY`/`positionX`/`positionY`/`rotation`) via `computePlacement` — see "Board / tile architecture" below. A message has no placement while pending or rejected; those fields are `null` until approval.

## Invitation management

- `InvitationRepository` gained `create`/`list`/`revoke` in EPIC 005, alongside the unchanged `getByToken`/`recordUse` from EPIC 002 — same interface, same repository pattern, no parallel storage. The admin UI (`/admin/invitations`) is the only place invitations are created; a token is `crypto.randomBytes(24)` base64url, not derived from the row id or anything guessable.
- Expiry is still computed, never stored, exactly as EPIC 002 established: `expiresAt` is a timestamp, and `getEffectiveStatus()` is what turns "past that timestamp" into the `"expired"` a page actually branches on. The stored `status` column only ever holds `"active"`, `"used"`, or `"revoked"` directly. Do not add a stored `"expired"` status or a cron job to write one — this is a deliberate, load-bearing decision, not an oversight.

## Board / tile architecture

- The public board's only read path is `messageRepository.listApprovedByTile(x, y, range?)` → `getTile()` in `src/features/board/repository.ts`, which filters to `status = "approved"` at the query level and maps down to the narrow `BoardTile*` contract (`src/features/board/types.ts`) before the data ever reaches a route handler or component — no `authorId`, `invitationId`, `status`, or moderation fields leave this layer. `GET /api/board?tileX=&tileY=` and `/board` (Server Component, for the initial tile only) are the only consumers; never fetch the full `messages` table for board rendering.
- Placement is deterministic and reproducible: `computePlacement(sequence, messageId)` in `src/features/board/lib/placement.ts` maps a Postgres-sequence-assigned slot number to a tile (via an outward square spiral from the origin) and a jittered position within a fixed grid inside that tile. The jitter is hashed from the message id, not random, so recomputing it later gives the same answer. **A published note's placement is permanent** — it is assigned once, at approval, and nothing recomputes or reshuffles it afterward (not on the client, not on re-render). Never re-run placement for an already-approved message.
- `messages_status_tile_idx (status, tileX, tileY)` and `messages_status_created_idx (status, createdAt)` are the indexes the tile query and moderation queue are built around — add new query patterns with an index in mind, not as an afterthought.
- `BoardPreview` (`src/features/board/components/BoardPreview.tsx`) takes an optional `notes` prop, defaulting to EPIC 001's curated `sampleNotes` — **the homepage preview is unchanged and stays this static component.** `/board` is a separate, unrelated experience (`InfiniteBoard`, below) — the two intentionally serve different purposes (homepage: invitation to discover; `/board`: actual exploration) and must not be merged.
- Time-exploration foundation: `listApprovedByTile`/`getTile`/`GET /api/board` all accept an optional `{ from?, to? }` range narrowing by `createdAt`. No UI exposes this yet (deliberately — don't add an unfinished timeline control); when a "This Week"/"This Month"/year-picker UI is eventually built, thread its selection through this existing parameter rather than adding a new query path.

## Public author privacy contract

- A `BoardTileMessage`'s `author` field is `null` for an anonymous note — not a name/image that the UI happens to hide. `getTile()` never even fetches a user record for an anonymous message's `authorId`; the identity behind an anonymous note never enters the function's return value at all, let alone the client. For a named note, `author.image` is resolved via `userRepository.getByIds` (one batched lookup per tile, not N+1).
- When adding any new public-facing board data, extend `BoardTileMessage` deliberately and re-check what it exposes — the default posture is "nothing beyond what's needed to render an approved note," not "whatever's convenient from the `Message`/`User` rows."

## Infinite board interaction model

- `src/features/board/components/InfiniteBoard.tsx` is the real exploration experience at `/board`: a pannable/zoomable world where tiles are positioned in world-pixel space (`TILE_PX` per tile, `src/features/board/lib/worldGeometry.ts`) and notes inside them reuse `Note` with `variant="world"` — never a second rendering system.
- Camera state (`x`, `y`, `zoom`) lives in one place: `useBoardCamera()` (`src/features/board/hooks/useBoardCamera.ts`), a plain reducer — no external state library. It reads an initial position from `?x=&y=&z=` on mount and writes back via a debounced (800ms) `history.replaceState`, so the URL never updates on every drag frame.
- During an active drag/pinch/held-key gesture, the camera's DOM transform is mutated directly on a ref/element (`applyTransform` in `InfiniteBoard`) for instant 60fps feedback, and only committed to React state via a `requestAnimationFrame`-throttled call. An `isGesturingRef` flag stops the "sync committed state back to the DOM" effect from firing mid-gesture, which would otherwise fight the live position with a slightly-stale one. Keep this pattern if you touch the drag/zoom code — removing the guard reintroduces visible jitter.
- Tile loading/caching/deduplication is `useTileCache()` (`src/features/board/hooks/useTileCache.ts`) — the only place that calls `/api/board`. It fetches exactly the visible-plus-one-tile-buffer range (`visibleTileRange`), never an entire region at once, dedupes in-flight requests, and prunes its cache past `MAX_CACHED_TILES` by dropping tiles farthest from the current view.
- Keyboard panning (arrow keys + WASD) is ignored whenever `document.activeElement` is a form control or content-editable — see `isTypingTarget`. Don't remove this guard when adding new interactive UI to the board page.

## MINDOT center

- World coordinate `(TILE_PX/2, TILE_PX/2)` — the center of tile (0,0) — is "MINDOT center." `BoardCenterMark` renders a low-opacity `BrandMark` and the localized `boardPage.slogan` there, as an ordinary world-space element (it recedes as you pan away because it simply falls out of view, not via separate fade-by-distance logic). `resetToCenter()` returns the camera exactly here. Keep this subtle — it is a starting point, not a permanent logo fixture.

## Memory preservation architecture

- `src/features/memories/` turns an already-approved, already-public message into a preservation output. It reads the message the same privacy-respecting way the board does — `getPublicMessageById()` (`src/features/board/repository.ts`) returns `null` for anything not `status = "approved"`, so a memory project can never be started from a pending/rejected/nonexistent message, and an anonymous message's real author never enters this feature's scope at all (same guarantee as `getTile`, just for one message).
- **Message author vs. memory creator are different people, modeled separately, on purpose.** `messages.authorId` is who wrote the thought; `memory_projects.createdBy` is who is preserving/buying it — never assumed to be the same user. Every memories Server Function checks project *ownership* (`memory_projects.createdBy === session.user.id`) for actions on a project, and never conflates that with anything about the underlying message's author.
- The board's "preserve this thought" entry point is a generic, optional `actions` prop on `Note` (`{ href, label }[]`, EPIC 008 generalized this from a single `action` to an array so the board could add "Share" alongside it), rendered inside Note's own existing hover/focus state — not a second wrapper element, which would have broken the percentage-based absolute positioning the `"world"`/`"board"` variants depend on. `InfiniteBoard` is the only place that passes it, pointing at `/memory/[messageId]` and `/share/[messageId]`.
- **Deterministic capture region**: `resolveCaptureRegion()` (`src/features/memories/lib/captureRegion.ts`) — for `"note_with_surrounding"`, the region is simply the note's own tile, queried via the same `getTile()` the public board uses. No client screenshot, no randomness: because approved placement is permanent, the same message + capture mode always reproduces the same region, and it's trivially server-verifiable (just re-run the query).

## PDF generation architecture

- `@react-pdf/renderer` (React-component-based, server-side, no browser/screenshot dependency) renders `MemoryPdfDocument` (`src/features/memories/services/renderer.tsx`) directly to a `Buffer` — `services/pdf.tsx` is the only place that calls it, always regenerating from source rather than caching a rendered file, so a download always reflects current data through the same deterministic capture region.
- **Unicode**: a Noto Sans (latin-ext) WOFF, embedded at `src/features/memories/assets/fonts/`, registered once via `services/fonts.ts`. Verified directly with `fontkit` before committing to this font — full glyph coverage confirmed for Turkish (ğşıöüçĞŞİÖÜÇ), German (äöüßÄÖÜ), French, and Spanish diacritics.
- **Visual rendering: confirmed, EPIC 013.** Generated real PDFs (every frame template, TR/DE/FR/ES/EN sample content, and a `note_with_surrounding` multi-note grid) through a real Next.js request and visually inspected the rendered output directly — every diacritic in every language renders correctly with no missing/substituted glyphs, across all five frame templates and both orientations.
- **Text-layer extraction: confirmed unreliable, EPIC 013 — this is now a characterized defect, not an open question.** The plain-text layer extracted from the same PDFs is frequently out of logical reading order (word fragments interleaved) whenever react-pdf's line-wrapping breaks a paragraph across two lines — reproducible on German/French/Spanish/English samples in this session. A short, single-line Turkish sample (no wrap) extracted correctly, consistent with the defect being specifically about multi-line paragraph layout, not Turkish-glyph-specific. One English sample also lost its leading capital letter (word "Every" rendered as "very") in the *visual* output itself, reproducibly, on the one word tested this way — plausibly the same underlying hyphenation-engine bug ("Every" hyphenates as "E-very"; `@react-pdf/hyphenate` is present in the dependency tree, defaults to an English dictionary, and was not explicitly configured off anywhere in this codebase) rather than a language-coverage issue, but this was only isolated for one word and not exhaustively characterized. **Practical implication: do not assume copy/paste text extraction is reliable from any generated Memory PDF; do not assume every possible word/wrap combination renders its leading character correctly.** The keepsake's printed/viewed appearance (what actually ships) is unaffected by either finding. A real fix would mean either disabling react-pdf's hyphenation (`Font.registerHyphenationCallback((word) => [word])`) or upgrading `@react-pdf/renderer`, and verifying carefully — out of scope for the EPIC that found this; don't attempt it speculatively.
- The renderer is a parallel implementation, not a second source of truth: note appearance comes from the same `noteTemplates` registry (`features/notes/config/templates.ts`) the real `Note` component reads, and the brand mark's dot positions are imported from `BrandMark.tsx`'s exported `DOTS`/`DOT_RADIUS` (not re-invented) — a parallel renderer only because PDF and DOM/CSS are different render targets that can't share components directly. `services/pdfPalette.ts` is a deliberate, documented exception: plain hex mirrors of `tokens.css`, since react-pdf can't read CSS custom properties.
- **PDF Download V2 (unframed projects).** `generateMemoryPdf` renders a project *without* a frame (personal PDF, physical gift) as `PdfDownloadDocument` (`renderer.tsx`), an 8×12in (2:3) page of three layers: (1) the designer's language-free background `public/images/pdf/mindot-pdf-background-v2-clean.png` (`pdfBackground.ts` — navy field, D mark + MINDOT wordmark, particles, rings, the glowing card frame; embedded once from raw bytes, never redrawn in code), (2) the card, drawn by the share image's own `MemoryNoteCard` (`pdfCardImage.tsx`, emoji and sports artwork intact, plus neighbour excerpt chips for `note_with_surrounding`) and centred inside the frame's dashed border, (3) text the background deliberately leaves out: the fixed slogan "AKLINDA KALMASIN." (`PDF_DOWNLOAD_SLOGAN` in `pdf.tsx`, the same in every language), the **generation** date — the card's template name is never printed — (`lib/pdfDownloadDate.ts`: day, full month name and year in the note's language, in the downloader's `cf.timezone`), and the domain from `PRODUCTION_SITE_URL`. The card's placement is measured against the asset's pixel geometry (`PDF_BACKGROUND_SIZE`/`CARD_WINDOW` in `renderer.tsx`) — re-measure if the artwork changes; never bake a slogan, date, domain or other language-dependent text into the background. Image-backed cards with a transparent centre (celebration-spark, congratulations-note) get the board's canvas tone under them, chosen by the artwork's own alpha. A **framed** project (digital frame) keeps the share "print" composition via `MemoryPdfDocument` — a paid, chosen frame is never replaced. The share image (`shareCardRenderer.tsx`, `noteCardSatori.tsx`, share routes) is not involved in V2; keep it that way, and keep every V2 layer inside the page bounds (a layer past the edge makes react-pdf add pages; `wrap={false}` renders blank).
- Never generate a PDF directly from a route/component without going through `services/pdf.tsx` — that's where the "message must currently be public" check happens (`MemoryPdfSourceUnavailableError` if not).

## Frame template architecture

- `src/features/memories/config/frameTemplates.ts` — the same registry philosophy as `noteTemplates`: a `FrameTemplate` (category, orientation, background/ink/accent colors, logo placement, `enabled`) is data, read by one renderer (`MemoryPdfDocument`), never a new component per frame. Add a frame by adding an entry; only add a renderer branch if a frame needs a structurally new layout, not for a new color/category.

## Digital product & access code flow

- **Architecturally prepared, not live-integrated** — there is no real Shoppier webhook/API anywhere in this codebase. `DigitalPurchaseProvider` (`src/features/memories/providers/types.ts`) is the abstraction a real integration would implement; `providers/manualProvider.ts` (`name: "manual"`) is the only one that exists, and it is honest about that — it doesn't verify any payment, it just records that a code should exist. `/admin/access-codes` is where an admin issues one today (manually, after confirming a sale happened elsewhere), lists every code, and can `revoke` an unused one.
- A `digital_access_codes` row starts with `memoryProjectId: null` — issued unassigned, since an external sale doesn't know MINDOT's internal project id yet. `DigitalAccessCodeRepository.redeem(code, memoryProjectId, userId)` is a single atomic conditional `UPDATE` (same pattern as invitations' `recordUse`) that only succeeds for a currently-`"active"`, unexpired code, and is what assigns the code to a specific project and flips it to `"redeemed"` — after that, the same code can never be redeemed again for a different project. This is the actual security boundary; verified directly (re-redemption against a different project fails). `revoke` uses the identical pattern — a conditional `UPDATE ... WHERE status = 'active'` — so a code someone has already redeemed can never be revoked out from under their access.
- `getRedemptionStatus(code)` is diagnostic only, never authorizing: `redeemAccessCode` always attempts the real atomic `redeem` first, and only calls `getRedemptionStatus` *after* that fails, purely to pick a precise user-facing message (`code-not-found`/`code-already-used`/`code-revoked`/`code-expired`). A race between the two can make a message a beat stale; it can never grant access it shouldn't.
- **Access state is re-derived from the database on every page load, never trusted from client memory.** `/memory/[messageId]` fetches the signed-in user's existing projects for that message and, for each `digital_frame` one, calls `getRedeemedForProject` fresh — so a user who redeemed a code yesterday sees "access granted" immediately today, with no code re-entry. Keep this pattern for any future state shown on that page: read it from the database on the server, don't reconstruct it from what the client happened to do earlier in the session.
- Downloading (`GET /api/memories/[projectId]/download`) is never a static file URL. It requires: signed in, and (owner of the project OR admin), and — for the owner — the entitlement the shared output policy names for the project's `outputType` (`features/memories/lib/outputPolicy.ts`, applied by `checkMemoryOutputAccess` in `services/outputAccess.ts`): a `memory_pdf_unlocks` row for `"personal_pdf"`, a redeemed code recorded against *that* project for `"digital_frame"`, and never for `"physical_gift"` (paid outside MINDOT, nothing in-app to verify — production reads it through the admin bypass) or any unknown type. The policy is an allowlist: a type or requirement it doesn't recognize is denied, never let through — the earlier per-type `if` branches let an unlisted, client-chosen `physical_gift` reach the renderer unpaid. Framed output always needs a paid entitlement, and `createMemoryProject` (`validateNewMemoryProject`) only accepts a `frameTemplateId` on `"digital_frame"` and only accepts `"physical_gift"` while `DILEKKUTUM_URL` is set. `?disposition=inline` (used by the admin order detail page's "View PDF") only changes the `Content-Disposition` header — same authorization, same generated bytes, the one and only PDF-generating code path. Never add a second endpoint or a second call to `generateMemoryPdf` for "preview" vs "download".

## Physical gift & DilekKutum flow

- **Architecturally prepared, not live-integrated** — no DilekKutum account/API connection exists. `createPhysicalOrder` creates a `physical_orders` row (status `"pending"`) and generates a human-typeable order number (`MND-2026-XXXXXXXX`, `features/memories/lib/identifiers.ts`) from a safe alphabet that excludes visually ambiguous characters (0/O, 1/I/L) — the buyer manually types this into DilekKutum's order note; nothing here talks to DilekKutum. `config/dilekkutum.ts` centralizes the destination URL (`DILEKKUTUM_URL`, defaults to the real storefront) — never hardcode that URL in a component.
- Status only ever moves via admin action (`updatePhysicalOrderStatus`, admin-checked independently like every other admin Server Function) through the states in `PHYSICAL_ORDER_STATUSES`. **That status enum was deliberately kept as-is in EPIC 007** (`pending → awaiting_dilekkutum_order → matched → in_production → packaged → shipped → completed`, plus `cancelled`) rather than replaced with a simpler suggested lifecycle — it's already a superset of operationally meaningful states, and Postgres enum values can be added but not cleanly renamed/removed without a much more invasive migration. Extend it (add a value) if a real gap shows up in practice; don't rename what's there without a good reason.
- `/admin/orders` is the list (order number, output type, customer, status, a link to detail); `/admin/orders/[orderNumber]` is the detail view — memory (note preview via the real `Note` component + frame/capture info), customer (name/email only — nothing DilekKutum-shipping-related is or should be stored here, since DilekKutum owns actual shipping), and production (status control + View/Download PDF, both going through the one download route above).

## Branded social sharing

- `src/features/sharing/` — turns already-public data (a board note, a wall-region capture, a Memory Project's framed output) into a branded PNG someone can share or download. It never re-derives privacy rules itself: every entry point reads through `getPublicMessageById`/`resolveCaptureRegion` (the same functions the board and Memory feature already use) before anything reaches the renderer, so an anonymous author's identity has already been stripped by the time `toShareCardNote()` (`features/sharing/lib/shareCardData.ts`) maps it into renderer input.
- **Automatic/scheduled social posting is permanently out of scope**, not deferred — confirmed explicitly in EPIC 008. Nothing here ever posts anywhere on its own; every share is a person deliberately choosing to share or download an image the app generated for them.
- **No third social-media API integration** either (no Instagram/TikTok/YouTube posting API) — sharing happens through the OS-level Web Share API or a manual download, never a direct platform API call.

## Branded export architecture

- `renderShareCard()` (`features/sharing/services/shareCardRenderer.tsx`) is the one renderer behind every share entry point — single note, wall region, and Memory Project. It takes a format + a primary note + optional surrounding notes + an optional `FrameTemplate`, never a `BoardTileMessage`/`MemoryProject` directly, so it never needs to know or re-derive where its input came from.
- Built on `next/og`'s `ImageResponse` (Satori → PNG), not `@react-pdf/renderer` — a genuinely different render target (raster image vs. PDF), so this is a second renderer by necessity, not a second source of truth: it reads the same `noteTemplates`/`frameTemplates` registries and the same brand-mark dot data (`BrandMark.tsx`'s `DOTS`/`DOT_RADIUS`, redrawn with plain positioned `div`s in `features/sharing/services/brandMarkSatori.tsx` — the same technique already proven through Satori in `app/icon.tsx` — rather than `<svg>`, whose Satori support is less exercised in this codebase). `pdfPalette.ts` (from `features/memories`) is reused directly for colors rather than duplicated a third time.
- **Fonts**: reuses the exact glyph-verified Noto Sans WOFF files from `features/memories/assets/fonts/` (`features/sharing/services/shareFonts.ts`) — never a second font asset for the same Turkish/German/French/Spanish coverage guarantee. `ImageResponse`'s `fonts` option takes raw bytes (`ArrayBuffer`), so — unlike the PDF renderer — no base64 data-URI conversion is needed here.
- **Format registry**: `features/sharing/config/shareFormats.ts` — `square` (1080×1080, priority default) and `story` (1080×1920, secondary), same registry philosophy as `noteTemplates`/`frameTemplates`. Add a future size by adding an entry; never write a new renderer for a new size.
- **Two generating endpoints**, mirroring the PDF download route's shape (one endpoint, one renderer call, query/param-driven variation — never a duplicate renderer for a "preview" case):
  - `GET /api/share/note/[messageId]/[formatId]?mode=note_only|note_with_surrounding` — public, no sign-in required, since the underlying content is already public board data. Gated only by `getPublicMessageById` (approved-only) and, for `note_with_surrounding`, the exact same `resolveCaptureRegion()` the Memory flow uses — never a second wall-region implementation. Cached aggressively (`public, max-age=3600, stale-while-revalidate=86400`) since approved placement is permanent, so the same inputs always render the same bytes.
  - `GET /api/share/memory/[projectId]/[formatId]` — requires sign-in + project ownership and the same shared output policy as `/api/memories/[projectId]/download` (purpose `"share"`): a redeemed access code for a `digital_frame`, the PDF unlock for a *framed* `personal_pdf`, denied for a framed `physical_gift` or unknown type; an unframed `personal_pdf`/`physical_gift` card needs nothing (the free wizard's outcome) — deliberately **without** the download route's admin bypass, since sharing is a personal action on your own memory, not an operational one. `Cache-Control: private, no-store`.
- **Single-note vs. Memory share, same renderer, different frame**: a plain board-note or wall-region share has no `frame` and gets the default MINDOT navy card style; a Memory share passes the project's own `FrameTemplate` (from `getFrameTemplate`) when one exists, so a `personal_pdf`/`physical_gift` project (which never sets `frameTemplateId`) still renders sensibly with the default style.
- **Web Share API + fallback**: `ShareCardPicker` (`features/sharing/components/ShareCardPicker.tsx`) is the one client component behind every "share this image" action — fetches the PNG, calls `navigator.share({ files: [...] })` when `navigator.canShare` accepts it (mobile, mostly), otherwise falls back to a plain `<a download>` blob-URL click. Reused by `/share/[messageId]` (single note / wall region) and the Memory outcome panels (`MemoryShareSection` in `MemoryPageContent.tsx`) — never a second implementation of this logic.
- `/share/[messageId]` is a short, direct flow (format + scope picker → share/download), deliberately separate from the multi-step `/memory/[messageId]` wizard — sharing a plain board note shouldn't require going through Memory Project creation.
- **Social links**: `features/sharing/config/social.ts` (`SOCIAL_LINKS`) — same centralization pattern as `DILEKKUTUM_URL`/`SHOPPIER_PRODUCT_URL`, but `null` by default for every platform (no real MINDOT social account exists yet), read from `NEXT_PUBLIC_SOCIAL_*_URL` env vars. `SiteFooter` renders a link only for a platform that's actually set — never a broken/placeholder link.
- **Open Graph / Twitter previews**: `metadataBase` is set on the root layout (reusing `AUTH_URL`, next-auth's own canonical production URL, rather than a second "site URL" env var) so relative OG image URLs resolve correctly. `app/opengraph-image.tsx` and `app/board/opengraph-image.tsx` are generic, DB-free, statically-generated branded images (`features/sharing/services/brandOgImage.tsx`); `app/memory/[messageId]/opengraph-image.tsx` is per-note and privacy-safe by construction (built on `renderShareCard`/`getPublicMessageById`, so it can never show anything the board itself wouldn't) — it falls back to the generic brand image for a missing/ineligible message rather than erroring, since a crawler hitting a stale link shouldn't see a 500. `/memory/[messageId]`'s `generateMetadata` builds its text description the same privacy-safe way — an anonymous note's author never appears in the description either.

## Personal space & user profiles

- `src/features/profile/` composes the existing `users`/`messages`/`memories` repositories into privacy-safe personal-space contracts — it never talks to Drizzle tables directly. The authenticated area is `/me` (chosen over `/my-mind`: it reads unambiguously as "your own account area" without inventing a second identity concept); the shareable public page is `/u/[publicId]`.
- **This is deliberately not a social profile.** No followers, likes, friend counts, social graph, or public activity feed exist anywhere in this feature, and none should be added later without a full re-scoping — see EPIC 009's explicit boundary. The framing is "a personal collection of thoughts that once existed in your mind," not a timeline.
- **Personal wall architecture — a finite flow layout, not `InfiniteBoard`.** A user's own approved messages are scattered across the *global* board wherever EPIC 003's spiral placement (`computePlacement`) happened to land them at approval time — they share no spatial neighborhood with each other. Reusing `InfiniteBoard`'s pan/zoom/tile-cache machinery for a personal wall would mean inventing a second, parallel placement system for no real benefit, so a personal wall instead renders as a plain responsive `flex-wrap` of `Note` (`variant="static"`) — see `features/profile/components/WallNotes.tsx`. Each note repeats the wall owner's name/avatar (matching how a named board note already looks) rather than a special "no attribution" note variant, so this needed zero changes to `Note` itself.
- **No "make my wall public" toggle exists, and none is needed.** A user's named+approved messages are *already* public on `/board`. A personal wall is a re-filtered view of the same already-public data, scoped to one author — it introduces no new exposure, so there's no visibility decision left for a toggle to make.
- The header shows a small avatar linking to `/me` only when signed in (`RootLayout` passes a narrow `{name, image}` session summary down to `SiteHeader`, the same "server fetches session, hands a safe summary to a Client Component" shape as `InvitePageContent`'s `sessionUser`) — unauthenticated visitors see the existing sign-in flow, unchanged.

## Public personal wall & anonymous privacy

- `messageRepository.listPublicByAuthor(authorId, options)` is the *only* read path a public wall or its share card is ever built from — filtering (`status = "approved" AND is_anonymous = false AND author_id = X`) happens in the SQL query itself, exactly like `listApprovedByTile`, never by fetching everything and hiding rows in the client. `features/profile/repository.ts`'s `getPublicWall`/`getPersonalWallByUserId` are thin wrappers over it, mirroring `board/repository.ts`'s `getTile`/`getPublicMessageById` pattern precisely.
- An anonymous message is invisible on **every** public surface tied to its author — the global board (already true since EPIC 004), the personal wall, the wall's share card, and the wall's Open Graph image — but still belongs to the author's own private archive (`messageRepository.listByAuthor`, `/me/archive`) and can still be preserved as a Memory Project by its own author, exactly as before. The owner's read (`listByAuthor`) and everyone else's read (`listPublicByAuthor`) are separate query methods, not one method with a client-side filter, so this guarantee can't be silently undone downstream.
- `PublicProfile` (`features/profile/types.ts`) is as narrow as `BoardTileAuthor`: `publicId`, `displayName`, `image` — no database id, no email, no role.

## Private archive

- `/me/archive` is the owner-only view of `messageRepository.listByAuthor` — every status, including anonymous and rejected messages, since those still belong to the author's own history even though they're never publicly attributed. `getPrivateArchive` never exposes moderation internals (AI categories/reason/confidence, `moderatedBy`) — a message's only visible state is one of `"pending" | "published" | "not_published"`, collapsing `rejected` into the same non-judgmental "not published" label rather than an admin-facing "rejected" term.
- Capped at the 60 most recently-created messages per query (both the archive and the personal wall) — an intentionally simple limit rather than a pagination system; the time-exploration filter (`?from=&to=`, `features/profile/components/TimeRangeFilter.tsx`, built on EPIC 004's repository-level range filtering) is the way to narrow further. A known limitation, not a silent truncation — see the EPIC 009 report.
- "View on board" reuses the *existing* `?x=&y=&z=` camera-position URL sync `useBoardCamera` already builds (EPIC 004) — computed directly from a message's own `tileX`/`tileY` via `TILE_PX`, no new board-side code needed.

## Memory Project library

- `/me/memories` (`features/profile/repository.ts`'s `getMemoryLibrary`) combines the project list, digital access history, and physical order history into one list, since they're the same underlying `MemoryProject` rows — a `digital_frame` project just carries digital status, a `physical_gift` project carries an order. No duplicate concept or table was introduced; every field comes from `memoryRepository`/`digitalAccessCodeRepository`/`physicalOrderRepository`, unchanged. PDF viewing/downloading reuses the one existing `GET /api/memories/[projectId]/download` route — never a second endpoint or a second renderer call.
- Per-project detail (source message, digital-access-granted flag, physical order status) is fetched via `Promise.all` across the project list, not a batched join — the same intentionally-acceptable small-volume pattern `/memory/[messageId]`'s `existingProjects` already used in EPIC 007, since a user's own project count is small in practice.

## Personal wall sharing

- `renderWallShareCard()` (`features/sharing/services/shareCardRenderer.tsx`) is a second composition in the *same* renderer `renderShareCard()` already lives in — same `ImageResponse`/Satori infrastructure, same font loading, same `BrandLockup`/`paperColorFor` helpers — never a new rendering technology. It renders a curated grid of several notes with equal visual weight (no single "primary" note), which is why it's a distinct function rather than a mode of `renderShareCard`.
- `GET /api/share/wall/[publicId]/[formatId]` is public, no sign-in required — a personal wall is public content, so (mirroring `/api/share/note`'s policy, not the Memory route's owner-only one) anyone can generate a share card for anyone's wall, the same way anyone can already view it. Built only from `getPublicWall`, so it inherits every anonymous-privacy guarantee above automatically. Cached for 5 minutes (`stale-while-revalidate=3600`) rather than a note card's aggressive 1-hour cache, since a wall's content changes every time its owner gets a new message approved — unlike a single note's permanent placement.
- **Curation algorithm** (`features/profile/lib/curateWallSelection.ts`): evenly-spaced indices across the whole ordered history (oldest → newest), not simply "the most recent N." Deterministic — the same dataset always produces the same selection, so a shared card never changes between refreshes — chosen over a pure "latest N" because it reads as a retrospective across time, closer to this EPIC's own framing than a recency feed would be.
- `/u/[publicId]/opengraph-image.tsx` reuses this exact curation + `renderWallShareCard` — privacy-safe by construction, and falls back to the generic brand image for an unknown/empty wall rather than erroring (same "never 500 a crawler" rule as `/memory/[messageId]`'s OG image).

## User profile data model

- `users` gained exactly one column for EPIC 009 — `publicId`, a random ~10-character opaque token (`features/users/lib/identifiers.ts`, the same safe alphabet as memories' order numbers/access codes, now shared via `src/lib/randomCode.ts`) — never the Google `sub`, never this row's own database id. It's nullable at the schema level (a `NOT NULL` column can't be added safely to a table that may already have rows, without a data-backfill migration) but every newly-created user row gets one immediately at insert time, with the same collision-retry pattern as `digitalAccessCodeRepository.issue`; `userRepository.ensurePublicId(userId)` idempotently backfills any row that predates this field. `/u/[publicId]` is resolved via `userRepository.getByPublicId`, never by iterating or by database id.
- Deliberately nothing else was added to `users` at the time — no biography, no follower/like counts, no social links, no location. (EPIC 011 later added `publicWallEnabled`/`publicWallDescription` — a visibility flag and a short bio, both additive — see "Personal wall visibility & curation" below; this remains otherwise true.) `drizzle/0003_powerful_moondragon.sql` is a real generated migration (`npm run db:generate`), additive only (`ADD COLUMN` + one new index + one unique constraint) — never `db:push`.
- `messages_author_created_idx (author_id, created_at)` is the index both `listByAuthor` and `listPublicByAuthor` are built around, mirroring how `messages_status_tile_idx`/`messages_status_created_idx` already exist for the board/moderation queries.

## Personal wall visibility & curation

- **Two independent, additive columns from EPIC 011** (`drizzle/0004_premium_nick_fury.sql`, additive-only `ADD COLUMN`, never `db:push`): `users.publicWallEnabled` (boolean, default `false`) and `messages.showOnPersonalWall` (boolean, default `true`). They answer two different questions and must not be conflated: `publicWallEnabled` is "can a stranger see *any* of this user's wall at all," `showOnPersonalWall` is "is *this specific* approved+named message part of it." Toggling one never touches the other, and neither ever affects the global board (`status`/`tileX`/`tileY` alone still drive that).
- **Defaults were chosen deliberately, in opposite directions.** `publicWallEnabled` defaults `false` — privacy-first, opt-in, a genuine behavior change from EPIC 009's "always visible" default, applied to existing users too. `showOnPersonalWall` defaults `true` — so the moment an existing user opts back into a public wall, everything that was already implicitly public under EPIC 009 shows up exactly as before, and curating individual notes out is a deliberate, separate, later action rather than something that silently already happened to them.
- **Three distinct states, kept distinct at the data layer, not just the UI.** `getPublicWall()` (`features/profile/repository.ts`) returns a `PublicWallResult` discriminated union — `{status:"not-found"}` | `{status:"disabled", profile}` | `{status:"ok", profile, description, notes}` — never a `null`/empty collapse. Critically, the `"disabled"` branch returns *before* any message query runs: a disabled wall's notes are never fetched, not filtered out afterward. `PublicWallContent`, the wall's `opengraph-image.tsx`, and `/api/share/wall` all branch on `status`, never on `notes.length` alone, so a disabled wall can never accidentally render real content through any of the three surfaces.
- **`getPersonalWallByUserId`** (used both by `/me`'s own "Your wall" preview and by `getPublicWall`'s `"ok"` branch) filters `listPublicByAuthor` to `status = "approved" AND is_anonymous = false AND show_on_personal_wall = true` — all in the SQL `WHERE`, never client-side. It is deliberately **not** gated by `publicWallEnabled`: the owner's own `/me` preview always shows what their wall *would* contain regardless of the toggle, since enabled/disabled only gates what a stranger via `/u/[publicId]` can reach.
- **The curation toggle's real security boundary is the repository method, not the Server Function.** `messageRepository.setShowOnPersonalWall(id, authorId, value)` is a single atomic conditional `UPDATE ... WHERE id = ? AND author_id = ? AND status = 'approved' AND is_anonymous = false` — the same "atomic conditional UPDATE is the actual boundary" pattern as `approve`/`reject`/access-code `redeem`. `features/profile/actions.ts`'s `setMessageWallVisibility` re-derives the caller from the session and never trusts a client-supplied user id, but a `null` result from the repository already collapses "not yours," "doesn't exist," "not approved," and "anonymous" into one outcome — the Server Function doesn't need to (and doesn't) re-implement that logic.
- **Metadata/OG personalization requires actual content, not just an enabled wall.** `/u/[publicId]`'s `generateMetadata` and its `opengraph-image.tsx` only use the owner's display name/content in Open Graph tags when `status === "ok" && notes.length > 0` — `"not-found"`, `"disabled"`, and an enabled-but-empty wall all fall back to fully generic `MINDOT` metadata/branded image, so a shared link's preview card never reveals a private or empty wall's identity even before someone clicks through.
- **Settings surface**: `WallSettings` (`app/me/_components/WallSettings.tsx`) is the one place a user changes `publicWallEnabled`/`publicWallDescription`, rendered inline on `/me` — no separate settings route. `ArchivePageContent`'s per-message "Add to personal wall"/"Remove from personal wall" action is the one place `showOnPersonalWall` changes, shown only when a message is `published` and not anonymous. Both call `features/profile/actions.ts`, never a repository directly.

## Scaling principles

- Do not implement backend infrastructure (further admin APIs, real Shoppier/DilekKutum integrations, commerce inventory, or any social-platform posting API) speculatively — add it only in the EPIC that requires it. (AI moderation and the memory/print foundation are no longer on this list — see the sections above.)
- The board is spatially-partitioned by tile, never "load everything" — see "Board / tile architecture" above. Share-card generation follows the same discipline: it renders from one resolved note + its own tile's neighbors, never the whole board. Personal-space queries follow it too: every archive/wall/memory-library read is a single, indexed, author-scoped query — never a full-table scan — with a documented small-volume exception only where EPIC 007 already established the same pattern (see "Memory Project library" above).
- Do not add followers, likes, a social graph, or a public activity feed even if requested casually later — MINDOT's personal space is explicitly not a social-media profile (see "Personal space & user profiles" above and EPIC 009's report).

## Safe area & viewport

- The root layout exports `viewport` with `viewportFit: "cover"` (Next's static viewport export — never a hand-written `<meta>`), so pages can use the whole screen on notched iPhones and Android edge-to-edge, and `env(safe-area-inset-*)` reports real values. Zoom stays enabled (no `maximumScale`/`userScalable`).
- Insets are read only through the `--safe-top/right/bottom/left` tokens (`styles/tokens.css`, `env(…, 0px)` — 0 on desktop). They're applied where content meets a screen edge: `SiteHeader` (`pt-[var(--safe-top)]`, background under the status bar), `SiteFooter` (bottom), `PageContainer` gutters (each side `max(gutter, inset)` — clears landscape notches on every page), `BoardControls`, `BoardDiscoveryPanel`, the mobile notification popover, and a base-layer `max-height` cap for every native `<dialog>` (`globals.css`). A new full-width or fixed element that touches an edge uses the same `max(gutter, var(--safe-*))` pattern — never per-device pixel values.
- Viewport units: vertically centered full-page panels use `min-h-page-panel` (svh with a vh fallback, minus header/footer allowance and insets); the board shell uses `min-h-board-shell` (dvh). Both are `@utility` classes in `globals.css`. Prefer them over a raw `calc(100vh-…)`.

## Component reuse

- Prefer extending an existing component in `components/ui` over creating a near-duplicate. Only add a new shared component when it's actually used in more than one place or is a clear architectural primitive.

## First-time onboarding

- `src/features/onboarding/` is a compact, four-step introduction to MINDOT (write → identity choice → human review → board → preservation), not a tutorial. `OnboardingModal` (`components/OnboardingModal.tsx`) is mounted exactly once, in the root layout, so it's present on every page but only auto-opens for a first-time visitor on the homepage (`pathname === "/"`) — a deep link (an invitation, `/write`, a shared note) is never interrupted by an unrelated introduction. It reuses `Note` (`variant="static"`), `Badge`, `Button`, and `BrandMark` rather than inventing new visual primitives, and reuses existing dictionary strings (`dictionary.moderation.anonymousBadge`/`namedBadge`/`statusPending`-equivalent styling, `dictionary.memory.outputPersonalPdf`/`outputDigitalFrame`/`outputPhysicalGift`) instead of duplicating translations for concepts that already have them.
- **Persistence**: `src/features/onboarding/lib/state.ts` stores a single value — `"completed"` or `"skipped"` — under `localStorage` key `mindot:onboarding:v1`, wrapped in try/catch like every other localStorage read in this codebase (private-mode/blocked storage never crashes the app, onboarding is just offered again next visit). Both reaching the final step's primary action and any early dismissal (the close control, Skip, Escape, or a backdrop click) write to this same key and are equally terminal — there is no partial-completion state. No database table or column was added: this is anonymous-visitor-compatible, refresh-persistent client state with no cross-device requirement, so a client-only mechanism fully satisfies the requirement without a migration.
- **Versioning**: the version lives in the storage key itself, not in a separate schema/version field. If onboarding content changes enough that returning users who already saw it should see a new version once, bump the key (e.g. `mindot:onboarding:v2`) in `state.ts` — the old value is simply orphaned under a key nobody reads anymore, so onboarding reappears exactly once for everyone with no migration or read-time comparison logic.
- **Manual reopening**: `OnboardingReopenButton` (rendered once, in `SiteFooter`'s legal link row) is the one reusable entry point back into onboarding after the automatic first-visit showing. It dispatches a plain `window` event (`requestOnboardingOpen`/`subscribeToOnboardingOpenRequests` in `lib/state.ts`) rather than lifted React state — the same decoupled-coordination shape the original homepage guide already used for its own dismiss action — so it works from any page without prop-drilling into the root layout.
- Built on a native `<dialog>` (`showModal()`/`close()`), which supplies top-layer stacking, focus trapping, and Escape-to-close for free — no hand-rolled focus trap. Escape (`onCancel`) and a backdrop click are both treated as an explicit skip, same as the visible Skip/close controls, so a user can never become trapped. Focus moves to the current step's heading on open and on every Next/Back. The per-step content transition is a plain CSS keyframe (`onboarding-step-in` in `globals.css`, using the existing `--motion-base`/`--ease-standard` tokens) gated by Tailwind's `motion-safe:` variant — reduced-motion visitors get the same content with no animation, never a degraded experience.
- Out of scope for this feature, deliberately: no embedded copy of `WriteThoughtForm`, no access-code/payment/Shoppier/DilekKutum detail, no per-step deep-link CTAs (Next/Back/Skip/Finish is the entire navigation surface) — the homepage's own hero and the footer's reopen entry point already get someone to `/write`. See "Scaling principles" — this stays a first-visit introduction, not a second onboarding-tutorial system to maintain.

## Production readiness

- Runtime configuration access is centralized in `src/lib/env.ts`. Importing it never requires credentials; feature entry points validate values only when invoked, preserving database-free and OAuth-free production builds. `NEXT_PUBLIC_APP_URL` is the public canonical origin, `AUTH_URL` is Auth.js's origin, and both are `https://mind-ot.com` in production — see "Production identity, SEO & social configuration" below for the full site-URL/brand strategy. Secrets are never `NEXT_PUBLIC_*`.
- `RuntimeConfigurationError` is developer-facing. Root `error.tsx` logs the actual exception server/client-side for diagnosis while rendering only a translated, non-technical message to visitors. Never include an environment-variable name, connection string, or error stack in user-facing UI.
- `/me`, `/admin`, `/invite`, `/memory`, and `/share` are explicitly `noindex`; public discovery belongs to `/`, `/board`, and privacy-safe `/u/[publicId]`. Dynamic personal-wall metadata continues to use only `getPublicWall`.
- Legal pages are launch drafts describing actual product behavior, not legal advice. They must receive professional review before public launch. No text may imply automated Shoppier or DilekKutum integration while those flows remain manual/provider-prepared.
- First-time onboarding (`src/features/onboarding/`) is client-persisted under `mindot:onboarding:v1` and introduces the same discover → write → identity choice → human review → wall flow without altering submission or moderation logic — see "First-time onboarding" above.
- `StatePanel` is the shared quiet loading/error/not-found primitive. Keep expected action errors as return values; use App Router error boundaries only for unexpected failures, following Next.js 16 conventions.
- The infinite board height is flex-derived from its route shell rather than subtracting a hardcoded header height. Preserve its existing gesture and keyboard architecture.

## Staging environment

- `staging.mind-ot.com` is a separate Worker, `mindot-staging` (`env.staging` in `wrangler.jsonc`); everything at the top level of that file is production and stays untouched by staging work. Never use preview URLs as staging.
- The deployment identity is the explicit `APP_ENV` (`src/lib/appEnvironment.ts`), a committed non-secret var on the staging Worker only. Unset means today's behavior (production under a production build, development otherwise). Never decide environment from the request hostname.
- Under `APP_ENV=staging`: `getAuthRuntimeConfig()` throws `EnvironmentIsolationError` unless `AUTH_URL` (and `NEXT_PUBLIC_APP_URL`, if set) is exactly `STAGING_SITE_URL`; `getDb()` inside a Worker requires the staging `HYPERDRIVE` binding and never falls back to `DATABASE_URL`; robots.txt disallows everything, the sitemap is empty, and the root metadata is `noindex`. Runtime enforcement is staging-only — production's side of the rules is covered by `npm test`, not by new runtime checks.
- OpenNext embeds every `.env*` value into the uploaded Worker bundle as runtime fallbacks (`.open-next/cloudflare/next-env.mjs`), so `npm run build:cf:staging` refuses to run next to any `.env*`/`.dev.vars` file — staging is built from a clean worktree. Staging migrations go through `npm run db:migrate:staging` (`STAGING_DATABASE_URL` from the shell only). The staging database is a fresh one, never a branch of production.
- `npm test` (`src/lib/appEnvironment.test.ts`, node:test via tsx) checks the isolation rules, the `wrangler.jsonc` staging block (separate name, fixed custom domain, no preview/workers.dev URLs, staging-only vars, never production's Hyperdrive id, no secrets as vars) and the migration journal. The manual Cloudflare/Neon/Google/Apple setup is listed in README's "Staging".

## Production identity, SEO & social configuration

- **Brand vs. domain.** The visible product name is always `MINDOT` — never a hyphenated or spaced variant (`Mind-Ot`, `Mind Ot`, `MIND-OT`). The production domain is `mind-ot.com` (canonical origin `https://mind-ot.com`); the hyphen belongs to the URL, never to on-screen copy, `<title>` text, or Open Graph `siteName`. Both are centralized in `src/lib/siteConfig.ts` (`SITE_NAME`, `SITE_TAGLINE`, `SITE_DESCRIPTION`, `PRODUCTION_SITE_URL`) — read from there rather than repeating either literal in a new route.
- **One site-URL function.** `getAppUrl()` (`src/lib/env.ts`) is the single place that resolves an absolute site origin, in order: `NEXT_PUBLIC_APP_URL` (the intended public site URL variable — no separate `NEXT_PUBLIC_SITE_URL` exists, deliberately, to avoid two variables meaning the same thing) → `AUTH_URL` (Auth.js's own canonical origin, kept as a compatibility fallback since the two are normally identical in this single-domain deployment) → `PRODUCTION_SITE_URL` from `siteConfig.ts` in a production build with neither set → `http://localhost:3200` otherwise, matching `npm run dev`'s own pinned port (`next dev -p 3200` in `package.json` — dedicated so it never collides with other locally-running projects' dev servers). Every consumer that needs an absolute URL — root `metadataBase`, `robots.ts`, `sitemap.ts`, the JSON-LD `url`/`sameAs` fields — calls this function; none hardcode a domain. Local development can never accidentally produce a production URL (no env var set → localhost, full stop), and a production deployment can never silently fall back to localhost (the production branch of the final fallback is the domain, not `localhost`).
- **Metadata & canonical strategy.** Root `layout.tsx` sets `metadataBase` once; every route's `alternates.canonical`/`openGraph.url` is a relative path resolved against it. Only genuinely public, stable routes get a canonical: `/`, `/board`, `/privacy`, `/terms`, `/community-guidelines`, and `/u/[publicId]` (whose canonical is fixed to the bare `/u/[publicId]` path regardless of its `?from=&to=` time-range query params, so a filtered view is never a separate canonical identity). Authenticated/personal pages (`/me`, `/me/archive`, `/me/memories`) and workflow pages (`/write`, `/invite/[token]`, `/memory/[messageId]`, `/share/[messageId]`, `/admin/*`) deliberately carry no canonical at all — each is `noindex`ed via its route-group `layout.tsx` (`robots: { index: false, follow: false }`), which is the actual signal, not a canonical pointing at a private URL. Don't add a canonical to a route mechanically; decide per-route whether it's meant to be a public search result first.
- **Open Graph / share cards.** Reuse the existing `renderShareCard`/`renderWallShareCard`/`renderBrandOgImage` renderers (`features/sharing/services/`) for any new preview image — never a second `ImageResponse` pipeline. Every existing OG image route (`app/opengraph-image.tsx`, `app/board/opengraph-image.tsx`, `app/memory/[messageId]/opengraph-image.tsx`, `app/u/[publicId]/opengraph-image.tsx`) is privacy-safe by construction (built only from `getPublicMessageById`/`getPublicWall`, so an anonymous author or a pending/rejected message can never appear) and falls back to the generic brand image for a missing/ineligible target rather than erroring. This is unchanged by this EPIC — verified, not re-built.
- **JSON-LD.** Root `layout.tsx` renders one conservative `WebSite` + `Organization` JSON-LD block (`StructuredData`, same file) built only from `SITE_NAME`, `getAppUrl()`, and whichever `SOCIAL_LINKS` are actually configured (see below) — no ratings, follower counts, founders, or addresses. Extend it only with information the app's own configuration genuinely represents; never with speculative content.
- **Social profile configuration.** `features/sharing/config/social.ts`'s `SOCIAL_LINKS` (`instagram`/`tiktok`/`youtube`, each `NEXT_PUBLIC_SOCIAL_*_URL` or `null`) remains the single source of truth for MINDOT's own social profile URLs. `SiteFooter` and the root JSON-LD both read it and render/list only a platform whose URL is actually set — **a field existing in this config does not mean an account exists**; it's architecturally ready, not live, until the matching env var is set to a real URL. Never hardcode a social URL into a component or metadata file.
- **robots.txt / sitemap.ts.** `robots.ts` allows the genuinely public surface (`/`, `/board`, `/u/`, `/privacy`, `/terms`, `/community-guidelines`) and disallows everything operational/private (`/admin/`, `/api/`, `/invite/`, `/me`, `/memory/`, `/share/`, `/write`) — this is a courtesy to well-behaved crawlers, **not** an access-control mechanism; every one of those routes is independently `noindex`ed at the layout level and, more importantly, still authorization-checked server-side exactly as before. `sitemap.ts` deliberately lists only the small set of stable public routes, not a database crawl of every `/u/[publicId]` wall or board message — see the comment in that file for why, and don't add per-entity enumeration without a compelling reason.
- **Explicitly not implemented, still, by this EPIC**: analytics, advertising/tracking pixels, cookie-consent tooling, newsletter/email campaigns, automatic or scheduled social posting, any social-platform posting API, real Shoppier/DilekKutum integration. Nothing here changes moderation authority, invitation security, digital access-code security, physical-order authorization, or message approval — those remain exactly as documented above.

- **`admin@mindot.dev` / `visitor@mindot.dev` are backing data, not sign-in-able accounts.** Their ids are fixed dev strings, not real Google `sub` values, so no real Google sign-in can ever produce a session matching them — they exist only so seeded messages/invitations/memory projects have a real foreign key to point at. - **`npm run db:verify` (EPIC 013, new)** — a plain `tsx` script (no new dependency; same mechanism `db:seed` already uses), not a new test framework. Exercises the real repository layer (`messageRepository`, `board/repository`, `profile/repository`, `memories/repository`) against whatever `DATABASE_URL` points at and asserts the privacy/ownership invariants documented throughout this file: anonymous authorship never reaches public output, pending/rejected messages are never publicly readable, `showOnPersonalWall=false` is excluded from the wall query itself, a disabled wall never returns `"ok"`, a redeemed/revoked/expired access code can never be redeemed, and Memory Project/physical-order ownership scoping holds. Written to run against the seeded dataset above — a check whose seed row isn't present is reported `[SKIP]`, not treated as a failure, so it degrades gracefully against a database that was seeded differently or not at all. This reads back through the same methods every route already uses; it is not a substitute for server-side authorization anywhere, only a regression check on it.

## Manual Testing Before Launch

This is the practical "how do I actually try this" companion to the architecture notes above — the checklist itself lives in README.md's "Manual QA" section; this is the sequence and context around it.

1. **Required environment variables** (`.env.example` is the source of truth — see its `(Required)`/`(Optional)` labels): `NEXT_PUBLIC_APP_URL`, `AUTH_URL`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `AUTH_SECRET`, `DATABASE_URL`, and `ADMIN_EMAIL`/`ADMIN_PASSWORD` (for `npm run db:create-admin` — not the seeded dev admin's, see below) are all required for a real local testing session. Everything else (`AI_MODERATION_PROVIDER`, `DILEKKUTUM_URL`, `SHOPPIER_PRODUCT_URL`, the `NEXT_PUBLIC_SOCIAL_*` links) is optional; by code, unset commerce config renders its explicit "not available yet" copy (`memory.shoppierUnavailable`) rather than a broken link — this is a code-review confirmation, not a click-through one, since reaching that panel requires a real signed-in session (see "Items Requiring Manual Browser Testing" territory in the EPIC 014 report).
2. **Starting the application**: `npm install`, then `npm run dev`. The homepage, legal pages, and static assets work with no database at all (`getDb()` is lazy — see "Database & repository pattern" above); anything touching `messages`/`users`/`memories` needs `DATABASE_URL` pointed at a real, migrated Postgres first.
3. **Preparing the database**: any real Postgres works — a local install, `docker run --name mindot-db -e POSTGRES_PASSWORD=password -e POSTGRES_DB=mindot -p 5432:5432 -d postgres:16` (README's documented option, verified working end-to-end in EPIC 014), or a hosted free tier. Then `npm run db:migrate`.
4. **Seeding test data**: `npm run db:seed`, then `npm run db:verify` to confirm the privacy/ownership invariants actually hold against what got seeded — see "Development seed data & test readiness" above for exactly what's created.
5. **Creating/accessing an admin account safely**: set `ADMIN_EMAIL`/`ADMIN_PASSWORD` (and optionally `ADMIN_USERNAME`) in `.env.local` and run `npm run db:create-admin`, then sign in at `/admin/login` with that email — Google sign-in never grants admin, regardless of email (see "Authorization / admin role" above). Never hardcode an admin user or add a bypass — the seeded `admin@mindot.dev` is backing data only, deliberately not a sign-in-able shortcut.
6. **Recommended testing sequence**: work through README's checklist in order — Visitor → Authentication → Writing → Moderation → Board → Personal space → Personal wall → Memory Project → Digital product flow → Physical gift flow → Admin. Each section's seed data is already in place after step 4; later sections (Memory Project onward) depend on having approved at least one message in the Moderation section first.
7. **Still intentionally manual/configuration-based**: real Shoppier purchases (no live product exists; `SHOPPIER_PRODUCT_URL` unset shows honest "not available yet" copy), real DilekKutum fulfillment (the order-number handoff is manual by design — see "Physical gift & DilekKutum flow" above), and issuing a digital access code for a real sale (`/admin/access-codes`, manual today by design — see "Digital product & access code flow" above). None of these are bugs to fix; they're the documented, deliberate state of those integrations.
